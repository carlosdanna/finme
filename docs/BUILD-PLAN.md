# FinMe — Build Plan & Prompt Playbook

Companion to `personal-finance-game-GDD-rev2.md` and `finme-TDD.md`.
This document covers: how to structure the repo, which tool to use, and the exact sequence of prompts to work through, each with a verifiable exit condition.

---

## Part 1 — Tooling

**Use Claude Code, not chat artifacts.** This project needs a repo, a test suite, and a headless harness that runs 10,000 simulations. That is outside what a single-file artifact can do, and the balance tests are the part of this project most likely to change the design — they need to be runnable on demand, not regenerated by hand.

**Stack recommendation:**

| Layer | Choice | Why |
|---|---|---|
| Language | TypeScript, `strict: true` | The engine is all numeric invariants; the type system earns its keep here |
| Build | Vite | Fast, zero-config, browser target matches the GDD |
| UI | React + Zustand | Zustand over Redux/Context: the engine owns state, the store is a thin subscription layer |
| Charts | uPlot (engine charts) or Chart.js | uPlot handles 1,560-point series without effort; Chart.js is friendlier if perf isn't tight |
| Tests | Vitest | Same toolchain as Vite, runs the engine headless in Node with no browser |
| Schema validation | Zod | Events and Logbook templates are data files; validate them at build time or content bugs become runtime crashes |
| Storage | `StorageAdapter` interface over `idb-keyval` | **Never call IndexedDB directly.** See Part 2b — this interface is what makes a native port cheap |
| Money | Integer cents, no library | Per TDD conventions. Do **not** add a decimal library; it invites float dollars back in |
| Installability | `vite-plugin-pwa` | Gives an install-to-homescreen path before any native work, and offline play for free |
| Device testing | Playwright, 390×844 default viewport | The default viewport in tests is a phone, not a desktop |

**Deliberately excluded:** no backend for MVP, no state management framework beyond Zustand, no game engine, no native shell until the PWA has been played on real devices.

## Part 2 — The single most important architectural rule

```
packages/engine/   →  pure TypeScript. ZERO imports from React, DOM, or any browser API.
                      Runs identically in Node and the browser. This is non-negotiable.
packages/sim/      →  headless harness. Imports engine only. Runs balance tests C1–C6.
packages/ui/       →  React app. Imports engine. Owns no simulation logic whatsoever.
packages/content/  →  JSON data: events, logbook templates, job definitions, constants.
```

If the engine ever imports from the UI, the balance harness stops working, and the balance harness is the thing that tells you whether the game teaches gambling. Enforce it with an ESLint `no-restricted-imports` rule in the first prompt, not later.

**`CLAUDE.md` should contain**, and this matters more than it sounds:

- The unit conventions from TDD §0 (integer cents, annual rates, `weekIndex` as sole time source)
- The engine-purity rule above
- "Constants marked **[F]** in the TDD are contractual — changing one requires a ruleset version bump and an entry in DECISIONS.md"
- "Never call an RNG inside a loop over an unordered map"
- "Every new event needs a golden-seed test"
- Pointers to `docs/GDD.md` and `docs/TDD.md` with a note to read the relevant section before implementing

## Part 2b — Mobile-first, and the native port

FinMe is a phone game that happens to run in a browser. Desktop is the wide breakpoint, not the design target. This has consequences beyond CSS.

### The conflict this creates with the GDD

**GDD §7 specifies hover tooltips for the glossary.** Phones have no hover. If the glossary is a `title` attribute or a hover-triggered popover, the single system the GDD calls central to its educational goal is invisible to the primary audience.

**Resolution:** every financial term is a **tappable inline affordance** — a dotted underline that opens a popover on tap (and on hover, on desktop, as a bonus). Never `:hover`-only, never `title`. Build one `<Term>` component in prompt 15 and route every glossary term through it. Same rule for the Debts panel's payoff projections and the annual review's real-vs-nominal explainers.

### Layout consequences

- **Bottom navigation, not a sidebar.** Six-to-eight panels don't fit in a phone sidebar. Use a bottom tab bar for the four primary destinations (Dashboard, Money, Life, Logbook) and route secondary panels through sheets.
- **The advance control lives in the thumb zone.** It is the most-pressed control in the game by an order of magnitude. Bottom-right, above the tab bar, reachable one-handed.
- **Event modals are full-screen sheets on mobile**, centered dialogs at `md:` and up. shadcn's Dialog and Sheet share an API closely enough to swap on a breakpoint.
- **The Debts panel table becomes a card list below `md:`.** A five-column table with APR, balance, minimum, and payoff projection is unreadable at 390px. This is the panel where the game does its most important teaching — it cannot be the one that degrades worst.
- **`dvh`, never `vh`.** Mobile browser chrome resizes the viewport; `100vh` produces a layout that jumps when the URL bar hides.
- **Safe-area insets** on the bottom nav and any fixed element: `env(safe-area-inset-bottom)`.
- **Minimum 44px touch targets**, which the +/− time steppers in particular must respect — they're small controls doing high-frequency work.

### Chart consequences

uPlot over Chart.js is now a firmer recommendation, not a toss-up. A 1,560-point net worth series on a mid-range Android needs to pan and pinch smoothly, and uPlot's canvas rendering handles it where SVG-based libraries stutter. Charts need explicit touch handling — pinch-zoom and drag-pan, with no reliance on hover for the tooltip; use tap-to-inspect with a persistent crosshair.

### What makes the native port cheap later

The engine purity rule already does most of the work: `packages/engine` is pure TypeScript with no DOM, so it runs unchanged inside any JS runtime a native shell provides. Two additions make the rest painless:

1. **A `StorageAdapter` interface**, defined in prompt 1 and implemented by `WebStorageAdapter` (IndexedDB + localStorage fallback). A future `CapacitorStorageAdapter` or `NativeStorageAdapter` drops in with no changes to the persistence logic in TDD §14. **No file outside the adapter may reference `indexedDB`, `localStorage`, or `window`.**
2. **No route-based navigation state in URLs.** Keep panel navigation in the Zustand store. URL routing behaves differently inside a native webview and is the most common source of port friction.

**Recommended path:** ship the PWA first, play it on real phones, then wrap with Capacitor if you still want stores. Capacitor wraps the built web app essentially as-is, so a well-behaved PWA is already 90% of a native app. Do not start native work before the balance tests pass — a native shell around an unbalanced game is wasted effort.

## Part 3 — Prompt sequencing principles

Learned constraints that shape the sequence below:

1. **One prompt never spans engine and UI.** Mixing them produces UI-shaped engine code.
2. **Every prompt ends with a runnable verification.** End each with "run the tests and show me the output." A prompt whose success you can't check is a prompt you'll have to redo.
3. **The C1 harness comes before any gameplay.** It can invalidate the design, not just the implementation. Discovering in month three that Moonshot is optimal is a catastrophe; discovering it in week one is a tuning session.
4. **Content is data, entered in batches, never inline in prompts.** Events go in JSON files validated by schema. Don't paste event definitions into prompts.
5. **Golden-seed snapshots from prompt 3 onward.** Fix a seed, snapshot the first 200 weeks of state, and fail the build on drift. This is your only defense against a refactor silently breaking every shared run.
6. **Keep prompts scoped to named files.** "Implement §5 of the TDD in `packages/engine/src/debt/`" beats "add debt." Naming the files bounds the context Claude Code has to load and keeps sessions fast.

## Part 4 — The prompt sequence

Eighteen prompts across six phases. Each is written to be pasted more or less as-is.

### Phase 0 — Scaffold

**Prompt 1 — Repo setup**

> Set up a TypeScript monorepo using npm workspaces with the structure in `docs/BUILD-PLAN.md` Part 2. Four packages: `engine` (pure TS, no browser or React imports), `sim` (headless harness), `content` (JSON data), `ui` (React + Vite). Configure Vitest at the root running against `engine` and `sim`. Add an ESLint rule that fails the build if `engine` imports from `ui`, React, or any DOM API. Set `strict: true` everywhere. Create `CLAUDE.md` with the unit conventions from TDD §0, the engine purity rule, and pointers to the docs. Don't implement any game logic yet — I want `npm test` to run and pass with zero tests, and `npm run dev` to serve an empty page.

### Phase 1 — Deterministic core *(the gate)*

**Prompt 2 — Time and RNG**

> Implement TDD §1 (time and the 4-4-5 calendar) and §2 (deterministic RNG) in `packages/engine/src/time.ts` and `rng.ts`. Include the full stream-name set from §2.2 as a typed union. Write tests that verify: MONTH_START_WEEK is derived correctly and sums to 52; `isMonthBoundary` fires exactly 12 times per year; two RNGs from the same seed and stream name produce identical sequences; two RNGs from the same seed and *different* stream names diverge immediately; and `normal()` consumes exactly two draws per call.

**Prompt 3 — Market generation**

> Implement TDD §3 in `packages/engine/src/market.ts` and `inflation.ts`: the GBM base process, the crash/boom regime overlay with per-asset betas, dividend schedules, and the AR(1) inflation path. Everything must be pre-generated at init from the `market` stream into materialized arrays — no RNG calls after initialization. Write tests verifying: the same seed produces a byte-identical price series; a 30-year run contains 2–5 drawdowns of ≥20% on SAFE; bonds show positive returns during at least 60% of equity crash windows; and the realized median annual log-return of each asset over 1,000 seeds matches the `μ_log` table in TDD §3.3 within 0.5 percentage points.

**Prompt 4 — The C1 harness** ← **do not skip or defer this**

> Build `packages/sim/harness.ts` and `packages/sim/tests/c1.ts`. The harness runs N seeded market histories and evaluates scripted allocation strategies against them — no player, no events, no jobs yet, just capital deployed at t=0 plus a fixed annual contribution. Implement the strategies from GDD Appendix C1: all-in SAFE, all-in MOON, all-in CRYP, 60/40 SAFE/BOND, and momentum-chasing. Run 10,000 seeds over 30 years and report, for each strategy, the 10th/25th/50th/75th/90th percentile terminal wealth plus the ruin rate (terminal below 50% of contributions). Print a table. **Then tell me whether the design passes: the speculative strategies must have a clearly worse median than SAFE while retaining a meaningfully fatter right tail.** If it fails, propose specific parameter changes and re-run — don't just report the failure.

*Stop here and read the output before continuing. If C1 fails, the fix is a tuning conversation, and everything after this point depends on it.*

### Phase 2 — Economic systems

**Prompt 5 — Income and tax**

> Implement TDD §6 in `packages/engine/src/income.ts` and `tax.ts`: gross pay for hourly and salaried, the annual raise formula including the `RAISE_INFLATION_FACTOR` lag, marginal bracket computation with CPI indexing, capital gains split by holding period with FIFO tax lots, weekly withholding on employment income only, and annual settlement. Tests: marginal vs. average rate computed correctly at bracket boundaries; a side-hustle-heavy year produces an under-withholding bill; a lot held 51 weeks is taxed at ordinary rates and 52 weeks at 15%; brackets indexed by CPI don't drift a player into a higher bracket on inflation alone.

**Prompt 6 — Debt instruments**

> Implement TDD §5.1–5.4 in `packages/engine/src/debt/`, one file per instrument, sharing a common `Debt` interface. Credit card with grace period and the "Never" payoff projection case, amortizing loans, BNPL with its three-strike escalation, payday loans with rollover. Tests: an amortizing schedule fully retires principal in exactly `termMonths`; a 30-year mortgage's first payment is 75–80% interest; the payoff projection returns `null`/"Never" when payment ≤ monthly interest; three payday rollovers cost 45% of principal with principal untouched; BNPL appears as a liability from the moment of purchase.

**Prompt 7 — Credit score**

> Implement TDD §5.5 in `packages/engine/src/credit.ts`. Thin-file state before 26 weeks (score is `null`, never a number), the five-component weighted formula, exponential decay on payment history, and the ±20/month movement cap. Tests: no score exists before the threshold; utilization at 9% and 10% both score 1.0 and 11% does not; a missed payment's impact halves after roughly 140 weeks of decay; the score never moves more than 20 points in a month.

**Prompt 8 — Owned assets and net worth**

> Implement TDD §4.2 and §8: net worth aggregation, car depreciation with the off-lot drop, and the home model (build it now even though it's v2 — the balance sheet shape needs it). Test the underwater case explicitly: a 60-month-financed car with 5% down must have `loanBalance > carValue` for roughly the first 30 months, and net worth must *decrease* on the purchase.

### Phase 3 — Player systems

**Prompt 9 — Vitals**

> Implement TDD §7 in `packages/engine/src/vitals.ts`: energy, mood, performance, and the anti-spiral guarantees. Then write the safety test from §7.4 as a property test: generate 500 random reachable states with mood and energy below 30, apply a rest-and-free-social-only strategy, and assert that every one recovers above 50 within 8 weeks. This test must never be marked skip.

**Prompt 10 — Jobs**

> Implement TDD §3.1/§6.2 job logic in `packages/engine/src/jobs.ts`: the tier system, the seeded `jobTimeline` availability schedule, application rolls using the `jobApplication` stream, the vehicle prerequisite, performance-driven warning and firing tracks, and the job-hop wage step. Put job definitions in `packages/content/jobs.json` with a Zod schema. Tests: application probability is bounded 5–95%; the availability timeline is identical across two runs with the same seed regardless of player behavior; the firing track requires sustained low performance, not a single bad week.

### Phase 4 — Events and narrative

**Prompt 11 — Event engine**

> Implement TDD §9.1–9.3 in `packages/engine/src/events/`. Slot pre-scheduling from the `eventSlots` stream, ticket pre-drawing from `eventSelection`, the gate and multiplier evaluation, weighted CDF selection over a **stably id-sorted** eligible pool, the effect applicator, and the formula evaluator for magnitude expressions like `"clamp(0.5*monthlyIncome, cpi*20000, cpi*250000)"`. Write a Zod schema for `EventDef` and validate all content at load. Tests: identical seeds produce identical slot weeks regardless of player state; two different states at the same slot with the same ticket can select different events; an empty eligible pool passes the slot silently rather than throwing; the formula evaluator rejects anything outside its whitelisted function set.

**Prompt 12 — First event batch**

> Implement the three fully specified events in TDD §9.4 as JSON in `packages/content/events/`, plus five more from GDD Appendix A of your choosing across different categories. For each, write a golden test: fixed seed, fixed state, assert the exact selected event and the exact resulting state delta. Then add a content lint that fails if any event is missing a `logbookKey`, has a choice with no effects, or uses an `id` that collides with an existing one.

**Prompt 13 — Logbook engine**

> Implement TDD §11 in `packages/engine/src/logbook/`: trigger evaluation, the priority cap of two entries per week, the quiet-entry cadence, variant selection from the `flavor` stream with 3-deep anti-repetition, and template interpolation. Draw stable run-scoped names (friend, advisor) from `startingDraw`. Write placeholder copy — three variants per key — in `packages/content/logbook/`; real writing is a separate workstream. **Critical test:** adding, removing, or reordering Logbook template variants must not change any simulation value for a fixed seed. Assert this by running a full 30-year sim, shuffling the template pools, re-running, and diffing final state.

**Prompt 14 — Tick pipeline**

> Implement TDD §10 in `packages/engine/src/tick.ts`, wiring every system built so far in exactly the specified order. Add a comment above the function stating that the order is contractual and part of the ruleset version. Then create the golden-seed snapshot infrastructure: run seed `4F2A9C1B` for 200 weeks under a scripted default strategy, serialize the full state, and commit it as a fixture. Any future change that alters it must fail CI. Also implement the advance-control interrupt conditions from GDD §2.1.

### Phase 5 — UI

**Prompt 15 — Core screens**

> Build the UI in `packages/ui`, **mobile-first — design at 390×844 and let desktop be the wide breakpoint**. Screens: dashboard with net worth chart and advance control, time allocation panel using **+/− steppers, not drag-and-drop**, budget panel, debts panel, investing panel, balance sheet panel, event modal.
>
> Layout rules from BUILD-PLAN Part 2b: bottom tab bar for the four primary destinations with secondary panels in sheets; advance control fixed in the bottom-right thumb zone above the tab bar; event modals are full-screen `Sheet` below `md:` and `Dialog` above; the Debts panel renders as a card list below `md:` and a table above, with the payoff projection visible in both; `dvh` not `vh`; `env(safe-area-inset-bottom)` on fixed bottom elements; every touch target ≥44px including the steppers.
>
> Build a `<Term>` component for glossary terms: dotted underline, **tap-to-open popover**, never hover-only and never a `title` attribute. Route every financial term through it.
>
> Build shared `<Money>` and `<Pct>` components using `tabular-nums`. Zustand store subscribing to engine state; no simulation logic in the store; **no navigation state in the URL**. Follow GDD §1's tone rules: no green checkmarks, no approving copy, no `destructive` styling on any financial figure, the "Never" payoff projection rendered in the same weight and color as any other number.

**Prompt 16 — Logbook, annual review, epilogue**

> Build the Logbook panel (scrollable, with annual reviews pinned inline), the annual review screen per GDD §4.2 with the year-over-year balance sheet, nominal-vs-real columns, and counterfactual lines, and the end-of-run screen with the epilogue Monte Carlo per TDD §12. The epilogue chart shows the 10th/50th/90th percentile bands against the all-cash counterfactual. No letter grade, no rank, no percentage-of-optimal anywhere in this UI.
>
> All charts use uPlot with explicit touch handling: pinch-zoom, drag-pan, and **tap-to-inspect with a persistent crosshair** — no hover-dependent tooltips. The annual review's year-over-year balance sheet is horizontally scrollable with a pinned first column below `md:`; it must not compress into illegibility on a 390px screen. Verify the full 1,560-point net worth series pans smoothly under CPU throttling.

### Phase 6 — Closing the loop

**Prompt 17 — Bankruptcy, persistence, and remaining balance tests**

> Implement TDD §13 (bankruptcy with all three branches and the full `DireState`) and §14 (replay-based persistence with 100-week checkpoints, JSON export/import, and the ruleset-mismatch banner). **Persistence goes through the `StorageAdapter` interface from prompt 1** — implement `WebStorageAdapter` (IndexedDB, localStorage fallback) and assert in a test that no file outside the adapter references `indexedDB`, `localStorage`, or `window`. Then write `packages/sim/tests/c2.ts` through `c6.ts` per GDD Appendix C and run all of them. Report pass/fail for each with the supporting distributions. For any failure, propose the minimal parameter change that fixes it and explain the collateral effects on the other tests before changing anything.

**Prompt 18 — PWA and device pass**

> Add `vite-plugin-pwa` with an offline-capable service worker, app manifest, and icon set — the game has no backend, so it should work fully offline. Then run a device pass: Playwright tests at 390×844 and 360×740 verifying that every panel is usable one-handed, no touch target is under 44px, no content sits under the safe-area inset, and no interaction depends on hover. Test the event modal, the time stepper, the Debts card list, and the `<Term>` popover specifically. Add a CPU-throttled performance check that the dashboard chart renders a full 30-year series in under 100ms and pans at 60fps.

**After that**, the remaining work is content volume — 37 more events and ~280 Logbook entries — which is writing, not engineering, and is better done in focused batches of 8–10 events per session with the schema and lint already enforcing correctness.

## Part 5 — Session hygiene

- **Start every session** by having Claude Code read `CLAUDE.md` and the specific TDD section in scope. Don't rely on it inferring which section matters.
- **Append to `docs/DECISIONS.md`** whenever a prompt produces a choice the TDD didn't specify. Six sessions from now you won't remember why `CRASH_RECOVERY_FACTOR` moved to 0.68.
- **Bump the ruleset version** in the same commit as any **[F]** constant change, never separately.
- **Re-run C1 after every market or tax parameter change.** It's cheap and it's the test that guards the design rather than the code.
- **Commit golden fixtures deliberately.** If a snapshot test fails, the correct first question is "did I intend to change simulation behavior?" — not "let me update the fixture."

## Part 6 — Where this is most likely to go wrong

Ranked by how expensive the failure is to discover late:

1. **C1 fails after the game is built.** Mitigated by prompt 4. Do not defer it.
2. **Engine purity is violated early** and the balance harness stops running. Mitigated by the ESLint rule in prompt 1.
3. **RNG consumption order drifts during a refactor**, silently breaking every shared seed. Mitigated by golden fixtures from prompt 14 — which is arguably too late; consider adding a minimal price-series fixture at prompt 3.
4. **Logbook content volume is underestimated** and the game ships with three variants per key, making it feel like a spreadsheet after twenty minutes. Mitigated by treating writing as a scheduled workstream, not cleanup.
5. **The UI is built desktop-first and "made responsive" later.** This never works — desktop-first layouts encode sidebars, hover, and wide tables as structural assumptions. Mitigated by designing at 390px in prompt 15 and by defaulting Playwright's viewport to a phone.
6. **Float dollars creep in** through one careless division. Mitigated by integer cents and a lint rule banning `parseFloat` in the engine.
